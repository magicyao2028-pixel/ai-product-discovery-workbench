# Product Tool Handoff

The repository produces tool-neutral artifacts. It does not claim native Axure, Visio, XMind, or MindManager files.

| Artifact | Typical product-tool destination | What should be preserved |
| --- | --- | --- |
| PRD Markdown | Word, Notion, Confluence, or a PRD template | problem, users, goals, exclusions, requirements, acceptance criteria |
| Low-fidelity screen flow | Axure, Figma, or another prototyping tool | screen purpose, fields, primary action, requirement link |
| Workflow trace | Visio, Mermaid, or process-mapping tool | step order, gates, owner, blocked states |
| Opportunity hierarchy | XMind or MindManager | evidence, problem, opportunity, requirement relationships |
| Traceability matrix | Spreadsheet, Base, or requirements system | stable IDs and evidence-to-acceptance links |

## Interview questions this supports

- Why did you select this problem instead of another one?
- Which evidence supports each requirement?
- What makes a requirement testable?
- Why is the prototype low fidelity?
- Which external actions are blocked and who can approve them?
- How would these artifacts move into design and development tools?

The strongest answer is the decision chain demonstrated by the repository. Tool names alone do not prove product judgment.
